# Data2G PR #65 and shorter PixelQSO frames

PixelQSO's project dependency now follows the upstream Data2G Git default branch, rather than pinning the PR commit. Upstream `master` contains PR #65 merged as `27236ec1c11ab5adc584d2d7a0d903d0fe1ea594`, plus a follow-up fix (`282fe9d`) to report receiver-accepted `MODES` codeword limits accurately. The current `uv.lock` resolves master to `27236ec1c11ab5adc584d2d7a0d903d0fe1ea594`; refresh it with `uv lock --upgrade-package data2g` to consume newer upstream changes. The upstream package metadata still says version `0.0.1`; `uv pip install --dry-run --reinstall --index-url https://pypi.org/simple 'data2g[tnc]'` found no published versions. Git default branch is therefore the available normal channel. The Python and native receive engines admit a burst large enough for a 256-byte KISS frame (plus its length and four control codewords) in non-ACK modes, within each mode's protocol codeword maximum. This is not an unlimited-duration receive setting. ACK modes retain the old cap. Do not transmit frames larger than 256 bytes under the assumption that PR #65 will accept them.

PixelQSO no longer patches Data2G's global `Accept.of` method in its Python host process. The local wrapper remains for PixelQSO's frame-associated receive-SNR metadata on KISS; that behavior is separate from the PR and is not supplied upstream. The manifest follows the upstream branch and the lockfile records its resolved commit for reproducible installs. An external, unmodified Data2G host can decode the 256-byte KISS frames without PixelQSO's receive-length override; such a host does not emit PixelQSO-specific SNR metadata. A previously installed older host or native executable will not gain the PR's receive capacity until updated separately.

`card_backends.py:data2g_max_frame_bytes` caps each application frame at 256 bytes and the advertised mode's available codewords (reserving the host's two-byte frame length and up to four control codewords). It additionally aims for a 16-second burst when feasible; narrow slow modes retain the smallest legal PixelQSO fragment even if it exceeds that target. PixelQSO's `PQI2` transfer header and per-card CRC/image digest are unchanged, so smaller fragments are readable by existing PixelQSO receivers. `Data2GHostBackend.estimate_seconds` follows the same fragment limit as the actual `DATA2G_ADAPTER.frame_card` transmission path. More fragments increase per-burst control/framing overhead and total airtime; without an ARQ, a lost fragment still prevents whole-card completion, though a shorter frame loses fewer pixels and is more likely to survive a fade. There is no claim of improved on-air recovery without an identified transmission and comparative recordings.

Verification: `uv lock --upgrade-package data2g && uv sync` resolved upstream `master` at `27236ec` and installed it. The focused Data2G runtime, mode-policy, and transport tests passed.
